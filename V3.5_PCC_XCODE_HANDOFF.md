## 1. Current wiring (verified against the repo)

The ticket says "four files." In reality only **two own a session**, and
`AutoFillCoordinator` does **not** build one (it delegates), so there is no
single switch point today.

| File | Role | Session sites |
|---|---|---|
| `AutoFillNLConstraintService.swift` | Auto-Fill NL parsing (`@MainActor final class`, owns `session: LanguageModelSession?`) | **2** — `prewarm()` and the lazy safety-net in `parse()` |
| `GameLogInsightsService.swift` | Game Log insights (session built off-main in a detached task) | **1** — `runInference(prompt:instructions:)` |
| `AutoFillCoordinator.swift` | Orchestrates Auto-Fill; owns an `AutoFillNLConstraintService`, **never a session** | 0 |
| `AutoFillConstraints.swift` | Constraint types / schema only — **no FoundationModels** | 0 |

### Construction sites (all identical shape today)
```
AutoFillNLConstraintService.prewarm()          ~:208   LanguageModelSession(instructions: instructions)
AutoFillNLConstraintService.parse() safety-net ~:249   LanguageModelSession(instructions: instructions)
GameLogInsightsService.runInference()          ~:128   LanguageModelSession(instructions: instructions)
```

### Availability checks (2)
```
AutoFillNLConstraintService.isAvailable        ~:185   SystemLanguageModel.default.availability
GameLogInsightsService.startInference()        ~:72    SystemLanguageModel.default.availability
```

### `respond(...)` call sites (where `response.usage` lives)
```
AutoFillNLConstraintService.parse()  ~:257   session.respond(to:schema:)          // preferred: constrained decoding vs a dynamic roster schema
AutoFillNLConstraintService.parse()  ~:266   session.respond(to:generating:)      // fallback: Generable type
GameLogInsightsService.runInference  ~:129   session.respond(to:)                 // plain prose
```

### Behavior that interacts with the change
- `GameLogInsightsService` already catches
  `LanguageModelSession.GenerationError.exceededContextWindowSize` (~:98) and
  retries on a trimmed 10-log prompt. The 32k window should make that retry
  path rare — **keep the catch** as a safety net regardless.
- `AutoFillNLConstraintService.parse()` already has a no-model path: if
  `isAvailable` is false it still honors deterministic pattern-rules and
  otherwise throws `.unsupported`. Preserve that.

## 2. Design — one shared model provider

Add a small provider so both owners stop deciding independently. Suggested new
file `Lineup Builder/STLLanguageModel.swift` (name to taste):

```swift
import FoundationModels

/// Single decision point for which FoundationModels backend the app's LLM
/// features use: PrivateCloudCompute on iOS 27 (32k context + reasoning),
/// on-device SystemLanguageModel otherwise. Every LanguageModelSession the app
/// builds should come from here.
enum STLLanguageModel {

    enum Reasoning { case light, deep }   // maps to the SDK's reasoningLevel — see CONFIRM #2

    /// True when ANY usable backend exists (PCC on 27 if eligible, else on-device).
    /// Replaces the two direct SystemLanguageModel.default.availability reads.
    @MainActor static var isAvailable: Bool { /* CONFIRM #4 */ }

    /// Returns a session on the best available backend, or nil if none is usable.
    /// Callers keep their existing respond(...) calls unchanged.
    @MainActor static func makeSession(instructions: String,
                                       reasoning: Reasoning) -> LanguageModelSession? {
        // if #available(iOS 27, *), PCC eligible -> LanguageModelSession(model: pcc, instructions:)   // CONFIRM #1
        // else on-device available            -> LanguageModelSession(instructions:)
        // else                                -> nil
    }
}
```

### Why a provider, not a one-liner in `AutoFillCoordinator`
The ticket suggested the switch point live in `AutoFillCoordinator`, but the
coordinator never builds a session — `AutoFillNLConstraintService` does, and
`GameLogInsightsService` builds its own on a detached task. A shared provider is
the only thing both can inherit.

### Callers after the change
- `AutoFillNLConstraintService.prewarm()` / `.parse()` →
  `STLLanguageModel.makeSession(instructions:, reasoning: .light)`; keep the
  `session?` optional, keep `prewarm()`.
- `GameLogInsightsService.runInference()` →
  `STLLanguageModel.makeSession(instructions:, reasoning: .deep)`. **Isolation
  note:** `runInference` is `nonisolated static` and runs on a detached task;
  if `makeSession` must be `@MainActor` (PCC availability check), build the
  session on the main actor and hand it into the detached work, or make the
  provider's session construction `nonisolated`. Resolve per CONFIRM #4.
- Both availability reads → `STLLanguageModel.isAvailable`.

## 3. CONFIRM IN SDK (do these first — they gate the design)

1. **PCC session construction.** How is a `PrivateCloudComputeLanguageModel`
   turned into a `LanguageModelSession`? Expected `LanguageModelSession(model:instructions:)`
   — confirm the init and the model's initializer.
2. **Where `reasoningLevel` lives** — on the model init, the session, or per-call
   `GenerationOptions` passed to `respond(...)`. This decides whether the
   `reasoning:` argument sits on `makeSession` (model/session-level) or is passed
   at the respond sites (per-call). Adjust the design accordingly.
3. **Overload parity (highest risk).** Does a PCC-backed session support the
   Auto-Fill overloads `respond(to:schema:)` (dynamic `DynamicGenerationSchema`)
   and `respond(to:generating:)` (Generable)? If PCC does **not** support dynamic
   schema, decide: keep the Auto-Fill *schema* path on-device and use PCC only
   for the insights prose, or route Auto-Fill through the Generable fallback on
   PCC. Do not silently lose constrained decoding.
4. **Availability API** for PCC (device eligibility + is it a main-actor call?),
   and how it composes with on-device availability for `isAvailable`.
5. **`response.usage` shape** — the token-count fields (input / cached / output /
   reasoning) for the telemetry in §4.
6. **Runtime failure / network.** PCC is a server model — how does a call fail
   when offline or ineligible, and should a PCC failure fall back to on-device
   for that call? Decide the fallback policy (at minimum: don't crash, degrade to
   the existing no-model / trimmed paths).

## 5. Guardrails (do not regress)

- **Protected numbers.** The model may *phrase* a fact but must **never be the
  source** of a pitch-count / rest-day number. This work touches only
  constraint parsing + insights prose. Do **not** route FairPlayRuleIntent or
  PitchEligibility answers through any model — they stay structured lookups.
- **Pro gate unchanged.** Inherits the existing Auto-Fill gate; no new paywall.
- **Graceful degradation.** Unsupported / no-backend must keep the current
  behavior: Auto-Fill honors deterministic pattern-rules or throws
  `.unsupported`; insights goes to `.unsupported` / trimmed prompt. Never a crash
  or a hang.
- **iOS gating.** All PCC code behind `if #available(iOS 27, *)`. Deployment
  floor stays **26.0**.
- **Free tier.** Confirm the app's first-time-download count is under **2M**
  before relying on no-cost PCC.
