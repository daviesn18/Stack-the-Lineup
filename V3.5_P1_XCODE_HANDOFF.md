## Why this doc exists

The integration + test work below was done in **Claude Code on the web**, which
runs in a Linux cloud container with **no Xcode / iOS toolchain**. Nothing here
was compiled or run. Everything was written against the real APIs in the repo,
but it all needs a Mac + Xcode 27 to build, test, and verify. This doc is the
checklist for that.

The three P1 feature branches were merged onto `claude/3-5-roadmap-f2ij61`
(clean, no conflicts), then one commit of test additions was layered on top.
Original branches, all cut from the same `main` tip, remain intact:
`feature/app-intents-supportedmodes`, `feature/app-intents-testing`,
`feature/hitting-archetype`.

## 1. Build on Xcode 27

Toolchain is Xcode 27 / Swift 6.4, `IPHONEOS_DEPLOYMENT_TARGET = 26.0` (Phase 0).
A clean build should succeed. Watch for:

- **New test file compiling into the unit target:**
  `Lineup BuilderTests/HittingArchetypeTests.swift` — confirm Xcode added it to
  the **Lineup BuilderTests** target membership (not the app target).
- The test target is **not** MainActor-default (Swift 6 migration note). All the
  models these tests touch (`HittingArchetype`, `Player`, `Team`,
  `TeamRulesAnswer`, `PitchEligibilityAnswer`) are `nonisolated`, so the new
  tests should compile without actor hops. If a test complains about main-actor
  isolation, that's the regression to fix, not the test.

> Reminder: an unsigned `CODE_SIGNING_ALLOWED=NO` build launch-crashes on the
> CloudKit entitlements. `BUILD SUCCEEDED` is not proof it runs — do a signed
> run (see §4).

## 3. Run the AppIntentsTesting UI suite (iOS 27)

Scoped, to dodge the UI target's full-run hang:

```sh
xcodebuild test \
  -scheme "Lineup Builder" \
  -destination 'platform=iOS Simulator,name=iPhone 17,OS=27.0' \
  -only-testing:"Lineup BuilderUITests/STLAppIntentsTests"
```

`STLAppIntentsTests` is `@available(iOS 27.0, *)` and drives the shipped intents
out-of-process. It asserts:

- **Pro-gate asymmetry:** `FillLineupIntent` (`.foreground`) ROUTES to the
  paywall and returns (never throws); `GameRecapIntent` (`.background`) THROWS.
- Entity resolution: `PlayerEntity` string query + `TeamEntity` suggestions run.
- Pro override honored by the real `isProNow()` gate end-to-end.
- Seeded player resolves by name.
- **NEW:** `FairPlayRuleIntent` (Free / `.background`) answers on a seeded active
  team without throwing or foregrounding.

> **Simulator App Intents caching:** if intents behave stale after a code change,
> a reinstall is not enough — **shut down and boot** the simulator. This bit us
> repeatedly while the code was already correct.

> The harness has no launch-argument hook, so app state (Pro status, seed roster)
> is arranged through the `#if DEBUG` control intents in
> `DebugTestControlIntents.swift`. These are `isDiscoverable = false` and never
> ship.

## 4. Manual verification (can't be automated here)

1. **Signed run launches.** Real signing → app launches (CloudKit entitlements).
2. **Shared-team archetype round-trip (the CloudKit risk).** On device/simulator
   A (Pro), set a Hitting Archetype on a player of a **shared** team. Confirm on
   the other participant's device that (a) the roster still decodes and syncs,
   and (b) ideally the archetype comes across. Then confirm a build **without**
   the field (or an older TestFlight build) still decodes the shared roster — a
   new field must never break decode for a coach on an older build.
3. **Pro-gate UX by voice.** With a non-Pro fixture, "Hey Siri, fill lineup" →
   app comes forward showing the paywall (not a silent dead end). "How did the
   Tigers do today?" → spoken Pro error, app does **not** open.
4. **Dialog double-print.** Trigger a Fair Play rule and a Pitch Eligibility
   answer from Spotlight and confirm the on-screen dialog text doesn't repeat the
   numbers already in the snippet table.

## 5. Layer 2 — iOS 27 App Intents enhancements (NOT yet written)

This is the one piece of P1 still to build. It was deferred specifically because
the ticket flags it **"[verify exact API in Xcode 27 SDK]"** and it couldn't be
compiled in the web session. All of it goes behind `if #available(iOS 27, *)`;
the iOS 26 path stays exactly as Layer 1 left it. A separate task card was queued
for this too.

### 5a. Clarifying / multi-turn follow-up

Goal from the ticket: Siri can ask a clarifying question.

- **Do NOT** force `FillLineupIntent` to ask "how many innings?" — it
  deliberately defaults to filling the whole game when no inning is given
  (`FillLineupIntent.lastInningIndex(for:requested:)` and its comment). A forced
  prompt regresses that.
- **Better fit:** when `team == nil`, there is **no active team**, and there are
  **multiple writable teams**, ask "Which team?" instead of throwing
  `STLIntentError.noTeam`. `TeamEntity(_ team: Team)` makes candidates trivial
  (`AppIntents/TeamEntity.swift`).
- **Verify in the SDK** before committing: the exact call
  (`$team.requestDisambiguation(among:dialog:)` vs `requestValue`) and its
  behavior on an **optional** `@Parameter` (`var team: TeamEntity?`). This
  optional-parameter interaction is the specific unknown that stopped it being
  written blind.

### 5b. Onscreen awareness ("this player")

- Adopt the iOS 27 App Intents onscreen-entity API so Siri can resolve "this
  player" / "this team" from what's on screen. **Verify exact symbol names in the
  Xcode 27 SDK.**
- This **overlaps** the `[P2] Spotlight semantic-index for entities` ticket
  (entity semantic-index contribution). Coordinate so it isn't double-built.

### 5c. After Layer 2

- Re-verify per intent that the Pro gate still **routes** to the paywall (never
  throws) for `.foreground` intents once modes/onscreen change.
- Extend `STLAppIntentsTests` to cover the new follow-up path.
- Decide whether onscreen-awareness is genuinely in v3.5 or slips to a later
  release; if it slips, ship 5a alone.
