# v3.5 P1 — Real-Device Test Checklist

Branch `claude/3-5-roadmap-f2ij61`. These are the checks that a simulator can't
cover (CloudKit sharing across two iCloud accounts, live StoreKit entitlements,
real Siri voice + interactive prompts, signing). Automated build/unit/UI tests
already pass — this is the human-on-a-device layer.

**Do #1 even if you skip everything else** — it's the only one that could
corrupt a real coach's shared roster.

Prereq: a **signed** build of this branch installed on a real device (unsigned
builds launch-crash on the CloudKit entitlements).

## 1. Shared-team archetype decode — CLOSED on device 2026-09-19 (3.5/47) ✅
**Update:** the scary failure mode (a shared roster *failing to decode* on an
older build) is now guarded in code. CloudKit syncs each team as a single JSON
blob (`CloudKitManager.encodeTeam`/`decodeTeam` → `JSONEncoder`/`JSONDecoder`),
and `HittingArchetypeTests` now pins that boundary: archetype survives the
single-Team blob, an older archetype-free blob decodes to nil, and an unknown
future key inside a player doesn't break the roster decode. So a decode-break is
no longer a realistic risk.

What's left is optional live confirmation, not a data-safety gate:
- [x] **Nice-to-have:** two accounts / two devices — set an archetype on A, confirm
      B still loads the shared roster and (on the new build) sees the value.
      ✓ Shared roster loaded on the second account (3.5/47). Archetype value
      round-trip is covered by `HittingArchetypeTests`. Also flushed out and
      fixed two real bugs in the process: silent share-accept failures
      (`1cb964b`) and a noisy DeviceToken insert-vs-overwrite (`e12f99e`).
- [ ] **Known nuance (not a bug):** if a coach on an **older** build edits and
      re-saves a shared team, the re-encode drops the archetype for everyone.
      That's inherent to any additive field. Decide if it's worth a mention in
      release notes; no code fix needed.

## 6. 🆕 [P2] Spotlight semantic-index contribution (iOS 27) — VERIFY-FIRST GATE
This decides whether the P2 `indexingKey` work is even needed. It is a **device
check that gates a refactor**, not a check of shipped code. Nothing was changed
in the entities for it — that's deliberate (see the finding below).

**Finding (from the Xcode 27 SDK, 2026-09-18):** `indexingKey` is only an
`@Property(indexingKey: \CSSearchableItemAttributeSet.…)` initializer parameter.
`PlayerEntity`/`TeamEntity` use plain `let` fields + a hand-built `attributeSet`
(the *classic* index path), so adopting `indexingKey` means converting them to
`@Property`-wrapped fields — a refactor of entities Siri, Shortcuts, the widget
URL scheme and 20+ tests depend on. Worth doing **only if** this device check
shows the classic path does NOT already surface players/teams in iOS 27's
semantic (natural-language) Spotlight results.

Prereq: signed build, a roster with a few players, let Spotlight settle a minute.
- [ ] **Exact term still works** (classic path regression): pull down on the home
      screen, type a player's name / jersey / team → the result appears and
      **tapping it opens that player** (PlayerFormView at Position Preferences).
- [ ] **Semantic/NL query**: try a descriptive phrase that is NOT a literal
      keyword (e.g. "my shortstop", "kids on the Tigers") → note whether players
      surface at all.
  - **If yes** → classic `attributeSet` already feeds the semantic index; the
    `indexingKey` refactor is **unnecessary** — close the P2 as "no code needed,
    verified on device".
  - **If no** → the `@Property`/`indexingKey` refactor is justified; proceed with
    it (branch off, keep the URL-scheme + tests green), then re-run this check.
- [ ] Also re-check `app-intents-no-roster-schema`: does the 27 SDK add a
      person/team App Intents schema that fits a roster? (Was absent at 26.5.)

## 7. 🆕 CloudKit merge stomp — locally-newer lineup wins (the source fix)
`Team.updatedAt` (stamped in `save()`, carried in the JSON blob) + the recency
guard `shouldApplyServerTeam` in `mergeCloudKitChanges` now skip a stale server
copy instead of overwriting a locally-newer team. The decision function is unit-
tested (`CloudKitMergeRecencyTests`, 7 cases) and the blob round-trip is pinned;
this live check confirms the end-to-end race and that genuine remote edits still
win. Two accounts / two devices on the SAME account for the owned case.

- [ ] **Local edit not stomped (owned):** on device A, edit a lineup and quickly
      background/foreground to force a fetch → the edit **survives** (does not
      revert to the pre-edit server copy). Repeat a few times to hit the race.
- [ ] **Genuine remote edit still wins:** edit team X on device B, let it sync,
      then foreground device A (which did NOT touch X) → A **shows B's edit**.
- [ ] **Shared read-write:** an assistant coach's edit to a shared team isn't
      stomped by a foreground fetch, and the head coach still receives it.
- [ ] **Shared read-only:** a received view-only team always reflects the owner's
      latest copy (recency guard never freezes it on a stale copy).
- [ ] **Legacy upgrade:** a team last saved by a pre-v3.5 build (updatedAt absent
      → .distantPast) still syncs normally; first edit on the new build stamps it.
